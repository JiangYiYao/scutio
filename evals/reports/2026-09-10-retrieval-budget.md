# 检索预算扩展与 Claude Code 动态工作流（2026-09-10）

架构调研已更正为2026年 Claude Code 内置 `/deep-research` 与 dynamic workflows。下文删除2025年 Claude Research、Jina、LangChain及 MiroFlow 旧实现的参考，将2026年官方机制作为本次分析依据。原预算实验及原始数据保留；它们没有使用动态工作流。

**把两组 SpaceX 研究的 web 操作上限从24增至48后，两组最终回答仍未分析 Terafab，检索摘要中也没有该项目的记录。**更多预算带来了已有线索的深入核查，尚未补上这次关注的覆盖缺口。这个结果不能证明加预算通常无效，也不能证明多 Agent 必然更好。

用户随后明确：重要研究优先保证覆盖和深度，默认并行分工；简单任务直接完成。已在现有协作说明中落实，未新增研究框架或子能力。下述预算是实验控制条件，不是 Scutio 日常研究配额。

## 执行前约定

协议于2026-09-10 09:48:00 UTC冻结。沿用[上一轮](2026-09-10-discovery-comparison.md)两个 SpaceX 执行者的独立上下文及同一候选 skill，分别给予额外24个 web 数组条目、最多8条搜索，累计上限48／16；另可做4次离线确定性计算。原始用户请求、截止日期与正文上限保持不变，不提示项目名、疑似遗漏或应该采用的检索方向。两组原回答和评分保留。

中性续跑指令为继续先前研究，取证方向自行决定，可以补充、修正或维持结论；两组唯一差别仍为是否加载冻结的候选 skill。没有给予 Terafab、芯片、资本开支或“检查遗漏”等方向提示。执行者禁止读主任务、其它实验和私人配置，也不能自行分派子任务。

主任务预先观察：Terafab是否出现在取证记录、是否读到原始关系、是否进入判断；以及其它发现、实耗操作和时间。观察目标未提供给执行者。每组只续跑一次，不为命中某项目重跑或单改一组条件。

这检验的是“原路径结束后得到更多预算会继续找到什么”，不是“从开始就给48次预算”的严格因果实验。续跑提示、已有上下文和网页结果变化均影响结果。检索轨迹由执行者撰写，主任务据实际参数复算；没有独立捕获全部原始网页返回。

### 更多预算实际用在了哪里

- **无 skill 组**先搜索 EchoStar 持股权益和 SpaceX 分部投入，随后集中于 EchoStar 交割、股数、母公司责任、税负与回购。新增了下跌情景和兑现条件，仍未形成完整税后净值。
- **候选组**继续调查 EchoStar 的债务、股数和诉讼，也补查 Google 算力合同与 Starlink V3 容量。14次页内定位占新增操作的过半，只有5次新搜索，说明更多余量主要被用于已有路径。
- **候选组的具体增量**是把长期合同期限与可取消条款联系起来。主任务复核了 [SEC 合同披露](https://www.sec.gov/Archives/edgar/data/1181412/000162828026041150/spacexagreementfwp.htm)：2026年底之后双方可以提前90天通知终止，故2029年的名义终止日期不足以证明全期收入锁定。这是有用的调查推进，但不能据此宣称整体研究覆盖改善。

e01新增第10个条目打开了包含 Terafab 的6月招股书，但日志仅记载取得元数据和搜索片段，没有记录读取相关正文。e02没有记录追查该项目。人工通读两组答案、查询和发现摘要后，也未发现制造供给、轨道计算与资本投入之间的目标关系被分析。因此应表述为“记录和回答没有体现”，不能断言名称从未出现在任何工具返回中。

两组的部分来源出现动态页面空白、PDF读取或截图失败；e01还说明截图引用存在但没有获得可见图像，不能算完成视觉核验。完整记录保留这些差异，没有把失败计作有效证据。

### 能得出的判断

本次续跑支持一个较窄的诊断：**增加预算可以让选中的分支更深入，却未自动促使执行者重新检查整体范围。**这与“财报及第一条证券线索占据后续检索”的路径依赖解释一致，但不是单次实验可以证明的普遍规律。48次也可能仍不够；从头给更多预算、换时间重测或改变分工，都可能产生不同结果。

Terafab作为覆盖诊断来自用户反馈，具体原始依据已记录在[上一轮补查](2026-09-10-discovery-comparison.md#用户指出terafab后的补查不计入原实验)。这次没有另做匿名六维评分，没有修改原分数，也没有对两份投资分析的全部财务、行情与诉讼主张重新认证。

[实验数据](2026-09-10-retrieval-budget.json) 保存原始回答、检索参数、发现和失败摘要、输出哈希与主任务计数。两次续跑完成后、修改协作规则之前，包内106个文件均核对为原冻结哈希；之后的协作改动不属于这次被测版本。

## 2026年 Claude Code 的动态工作流

### 已确认的官方机制

Anthropic于2026年5月28日发布 dynamic workflows；发布页目前已更新为正式可用状态，当前全文不能当作首发功能快照。它允许 Claude 为任务生成编排脚本，将大量子任务交给运行时执行。[2026年发布说明](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code)

6月2日技术文章明确介绍 Claude Code 内置的 `/deep-research`：多角度搜索、取得来源、独立反驳与核查主张，最后综合引用报告。文章另展示可组合的模式，包括生成后筛选、独立验证、竞争方案和满足条件后才停止的循环；这些通用模式不能一概当成内置研究脚本的具体实现。[2026年技术文章](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)

**区别在执行结构：普通 subagent 委派由主 Agent逐轮协调；workflow 将循环、分支和中间变量放入 JavaScript，由对话外运行时执行。**后者可以保存和重新运行编排，并复用运行结果；子 Agent本身仍有上下文和材料选择限制，不代表全部证据无损保存。[运行机制](https://code.claude.com/docs/en/workflows#how-a-workflow-runs)

当前文档还说明，内置 `/deep-research` 对主张交叉核查并投票，过滤未通过核查的内容；限流或 API 错误导致无法检查时，列为未核实，不能算作已反驳。公开示例包含 `agent()`、`pipeline()`、`parallel()` 及结构化返回，但示例是路由审计，不能充当内置研究源码。[内置工作流及脚本示例](https://code.claude.com/docs/en/workflows)

本次依据为2026年官方文章、当前文档及公开示例，没有读取或运行 `/deep-research` 的完整内置脚本。因此不推定其精确 Agent 数、搜索拓扑、投票阈值或补搜轮次，也不把第三方模板标作官方实现。5月发布、6月技术说明和9月所读的滚动文档分别标注，避免混淆时点。

### 对上一版判断的纠正

“强模型已经会规划、搜索和综合”不足以说明这种架构没有价值。动态工作流提供的是对话之外的任务状态与执行控制，能明确安排独立探索、逐项核验、汇合和后续分支。它与在 skill 中增加研究建议处于不同层面。

上一版仅把重要研究改成默认多 Agent，落实了用户的投入偏好，却没有实现这里的动态工作流。原24→48续跑只观察两个单 Agent的既有路径，不检验这种执行结构；不能据其遗漏得出动态工作流无效，也不能因架构更复杂就断言有效。

## 对 Scutio 的具体适用判断

Scutio 当前是研究说明、数据工具和记录程序组成的 skill，没有提供执行 Agent任务图的运行时。Claude Code 的脚本调度、并发队列、结果持久化和中断恢复由宿主实现，不能通过修改 skill 获得。下述方法可以借鉴，完整执行机制需要另行确认宿主支持，不作为当前迁移承诺。

| 层次 | Scutio当前适合承担的范围 |
|---|---|
| 研究方法 | 重要方向探索、独立核查要求、关键证据与缺口记录、根据新发现继续调查 |
| 宿主协作能力 | 有原生 subagent 时动态分派和追问；没有时由同一 Agent分步研究，不能宣称具备同等独立性和并行规模 |
| 工作流运行时 | 脚本执行、任务依赖调度、持久化、重放与断点恢复由支持它的宿主承担；本项目未实现，也不作为安装 skill 的要求 |

目前建议继续在现有 skill 中验证研究方法与原生协作的收益；对特定宿主的动态工作流，可作为可选适配另行验证。自建跨宿主调度框架会增加 Agent接口、状态和恢复语义的维护范围，尚无本轮证据说明有必要。不能将“按发现调整分工”的提示要求等同于可靠执行的任务图。

以下是针对本项目问题提出的方法和可能的适配方向，不是声称 Claude Code 内置实现逐项采用了这些规则。

**按研究对象生成本次任务图。**以用户的范围和研究期限为起点，先从不同原始材料识别业务、重大变化和关键关系；再按新发现产生问题。分工粒度可以落到一个项目、一份合同、一条客户关系或一个可被推翻的假设，不必长期固定为“财务研究员、技术研究员、风险研究员”。复杂研究可以持续产生许多子任务，实际同时运行的数量由宿主能力决定。

**让新发现改变后续调查。**例如某份合作方公告出现大额投资，下一批任务应围绕它与目标公司的关系、承担投入的主体、关键技术依赖和商业兑现展开。核查如果发现主体或日期错了，就修正关系并停止错误分支；如果只是没有取到正文，则保留缺口并改查其它原始披露。这比让多个 Agent各交一份完整公司报告更符合本次遗漏问题。

**保留可核验的中间材料。**复杂研究中的来源、主张、定位、时点和取证状态应能跨任务传递；主任务需要时可以回到原文。采用宿主原生工作流时由其运行状态承载；其它环境可以在本次任务中使用结构化产物。普通问答仍自然表达，不给所有用户创建档案，也不复制一套长期数据库。

**分开检验事实和投资解释。**独立核查者可以检查来源是否支持某事实、是否存在反证和口径错配；投资判断还要连接约束变化、受益主体、再投资和价格条件。多个 Agent同意不能直接证明某股票值得买。核查应返回依据和未解决问题，使后续任务能够继续补证。

**既核查已有主张，也检查没有进入任务图的方向。**对本次 SpaceX 问题，逐项核验星链用户数和 EchoStar 条款，即使全部正确，也无法弥补从未研究制造供给与轨道计算关系的遗漏。因此需要独立的范围检查，并允许它产生新的调查分支。Terafab仅作为本轮失败诊断，不应写成所有公司研究的必搜词。

**根据调查推进情况收束。**重要任务优先覆盖和深度，不沿用本轮小配额；关键可查问题仍会改变判断时继续调查。结论成立、分支被排除或关键材料确实不可得时，保留理由。无法取证与反证成立分别表达，已有一个局部结论或全部子任务返回均不能单独证明研究完成。

## 本轮改动与验证边界

保留前一轮已落实的默认并行、简单任务直接完成和关键遗漏复查原则；本次纠正的是调研对象、技术依据及后续方向，没有将文档修订包装成动态工作流已经接入。

[研究协作](../../skills/scutio/references/methods/pipeline.md)目前仍为宿主 Agent执行的说明。要实现上述编排，需在宿主实际支持的能力上检验动态派发、结构化结果、独立核验与失败后的继续处理；不能只写出 Claude Code专有 API名称就声称所有宿主兼容，也无需预先引入旧研究框架。

后续验证重点应从“有没有派 subagent”改为：初始范围遗漏能否被发现，新关系是否触发调查，关键主张是否独立核对，读取失败是否被保留，跨分支关系是否进入最终判断。使用干净上下文和跨行业案例；若研究协作的独立贡献，再设可比总资源的对照，并统计所有研究与核查任务的实际用量。产品研究遵循覆盖与深度优先的偏好。

原两个新增行为用例及一个修订用例仍是定义，未执行；原说明一致性审查不验证研究效果。预算续跑数据保持冻结，**本轮尚未执行动态工作流的研究效果实验**。
